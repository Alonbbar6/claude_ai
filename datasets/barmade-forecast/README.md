# BarMade forecasting dataset (synthetic)

Training and evaluation data for the kitchen's **inventory intelligence**: when an ingredient
will run low, what will expire, what to reorder — plus the **kitchen ready-time** model the
iPhone app runs. Generated by a deterministic simulation of one restaurant, using the team's
own catalog (`customer-web/data/barmade`: 30 ingredients with suppliers, pack sizes, delivery
days and shelf life; 17 recipes), so every id, unit and JSON shape matches the live BarMade API.

```bash
node datasets/barmade-forecast/generate.mjs                 # 180 days, seed 42 → out/
node datasets/barmade-forecast/generate.mjs --days 365 --seed 7 --out /tmp/ds
node datasets/barmade-forecast/evaluate.mjs                 # baselines on the test split
node datasets/barmade-forecast/evaluate.mjs --predictions my_preds.csv
```

Nothing is real: no customers, no production records. Different seeds give different histories
with the same structure, so you can train on one seed and test on another.

## What's in `out/`

| File | Rows | Use |
|---|---|---|
| `inventory_daily.csv` | one per ingredient per day | **The main supervised table** (features + labels, below) |
| `kitchen_times.csv` | one per order | Ready-time model: features + `minutes_to_ready` |
| `orders.json` | one per order | Exactly the BarMade API's order shape (`items`, `consumed` with batches, `statusHistory`, `channel`, `source`, `fulfillment`) — for anything that will later read the real `/api/orders` |
| `movements.csv` | one per stock movement | `delivery`, `sale`, `prep_usage`, `waste`, `cancel` — the API's `/api/inventory/movements` shape |
| `batches.csv` | one per delivered batch | arrival, expiry, consumed, wasted, remaining (FIFO by expiry, like the API) |
| `daily_sales.csv` | one per day | orders, revenue, **lost sales from stock-outs** |
| `ingredients.json`, `menu.json` | catalog | supplier, pack size, lead time, delivery weekdays, shelf life, minimum stock; recipes |
| `splits.json` | — | train / val / test by `business_date` (70 / 15 / 15 %) |
| `metadata.json` | — | seed, parameters, scenario stories, counts |

## `inventory_daily.csv`

Features (known at the end of that day):
`date, weekday, ingredient_id, category, supplier, pack_size, lead_time_days, shelf_life_days,
minimum_stock, opening_stock, delivered, usage_sale, usage_prep, waste, closing_stock,
expiring_within_7d_qty, avg_usage_7d, avg_usage_14d, is_festival, is_storm`

Labels (computed from the future; blank where the horizon runs past the end):

| Label | Meaning |
|---|---|
| `usage_next_7d` | total sale + prep usage over the next 7 days |
| `days_to_runout` | days until `closing_stock` would hit zero at the **actual** future usage **with no further deliveries**; `30+` if it lasts a month |
| `runout_within_7d` | 1 if `days_to_runout` ≤ 7 — the "about to run low" alert |
| `waste_next_7d` | quantity discarded (expired + spoilage) over the next 7 days |
| `stockout_today` | 1 if closing stock is zero |
| `lost_sales_day` | revenue lost that day because something was out (same for every ingredient that day) |

Evaluate on the **test** dates only; the 7/14-day averages are rolling, so no leakage.

## `kitchen_times.csv`

Features: `hour, weekday, is_rush, is_weekend, item_count, prep_prior_min, busy_open_tickets`.
Labels: `minutes_to_ready` (as the kitchen tapped it), `true_minutes_to_ready` (without the
forgetting), `forgotten` (1 = the kitchen tapped READY 45–180 min late; the live API has these
too), `cancelled`. `kitchen_factor` marks the three "slow cook" weeks (×1.3) — a model that
learns from recent history should adapt; the fixed prior can't.

## What the simulation contains (so you know what a model can and can't learn)

- Demand by weekday (Sat ≈ 1.6× Tue), lunch and dinner peaks, slow growth, Poisson noise,
  one **festival** day (×2.3) and one **storm** day (×0.35) — see `metadata.json → stories`.
- Recipes with the web app's modifier math (extra cheese ×1.5 mozzarella, add chicken +120 g).
- FIFO consumption by expiry; expired batches discarded at opening; random spoilage of
  perishables; small daily prep usage for sauces, dairy, bakery and produce.
- A human manager who orders on each supplier's delivery days from a naive 7-day average with
  a lead time, **forgets 6 % of the time** and gets **short-shipped 4 %** — that's where the
  run-outs and lost sales come from.
- Kitchen timing from the same generative process the old server's ready-time model was trained
  on, scaled by the slow-cook period; 2 % forgotten tickets, 2 % cancellations.

## Baselines (`evaluate.mjs`)

- **Usage**: 14-day trailing average — this is literally what the BarMade API's
  `/api/inventory/forecast` does — and 7-day. Metrics: MAE, WAPE.
- **Run-out**: `closing_stock / average` → days; precision/recall of the ≤ 7-day alert.
- **Waste**: `expiring − expected usage`.
- **Ready time**: the iOS `ReadyTimeModel` prior (p50 MAE, p75/p90 band coverage).

Beat the 7-day average on usage WAPE and the run-out recall without losing precision, and the
model is worth shipping. For ready time, the prior is already calibrated on normal weeks; the
win is adapting during the slow-cook weeks and detecting forgotten tickets.

## Findings so far (seed 42)

| Model | Normal weeks | Slow-cook weeks | 2 weeks after recovery |
|---|---|---|---|
| iOS prior only | 1.94 min | 10.77 min | 2.05 min |
| learned, 28-day window | 1.75 | 5.54 | 8.17 |
| learned, 14-day window | 1.63 | 2.26 | 7.73 |
| learned, 7-day window | 1.63 | 2.02 | 4.86 |
| **learned, 3-day window** | **1.64** | **2.02** | **3.05** |

The learning helps a lot when the kitchen changes pace and costs nothing on normal weeks, but
long windows remember a bad week for too long. The iPhone app fits on the last 3 days (7 if
fewer than 8 tickets).

## Scoring your own model

Write a CSV with `date, ingredient_id, usage_next_7d_pred` (and optionally
`days_to_runout_pred`) for the test dates and run
`node evaluate.mjs --predictions my_preds.csv`. Any language is fine — pandas reads the CSVs
directly; `orders.json` is one array.
